# Persona run, set 1: findings (2026-11-23)

Six personas (`../PERSONAS.md`) drove the real window in headless Chrome
against a sandboxed dispatcher (debug build of the working tree, production
timings) and a simulated Claude Code fleet. 49 steps, all completing after
harness fixes. Raw data: `results/set1-2026-11-23/` (gitignored; regenerate
with `node run.mjs`).

Each finding is marked **confirmed in code** (the cause was read in the
source), **observed** (seen in the run, cause not traced) or **sim** (an
artefact of the simulation, so it says nothing about the real thing).

The fleet and solo paths are mostly quick. Time goes to three places:
**remote hosts** (mostly waiting, and nothing tells you why), **worktree
lifecycle** (git-bound waits plus extra confirmations), and **triage at
scale** (finding the session that is actually blocked).

## Findings, by where a user loses the most time

### 1. A host that drops makes its sessions vanish, with no word why (Rhea)
Confirmed in code. When a poll fails, `RemoteFleet::poll_host`
(`rust/imperatorium/src/remote.rs`) stores an empty row list, so the host's
sessions leave the board. The sidebar says "no sessions". Host status exists
(`/api/hosts`), but the main window never calls it. Measured: the tile went
14.6 s after the host dropped, and came back 26 s after the host returned.
There is no way to poll again from the window. A prompt typed while the host
was down went nowhere: no tile, no pending note.
*Direction:* keep the host's last rows, marked unreachable, with the error and
a "retry now"; show host state in the sidebar.

### 2. Send is greyed out on remote sessions, but Enter sends (Rhea)
Confirmed in code. `drawHead` sets `#send.disabled` for any `s.remote`, while
the prompt box's Enter calls `send()`, which has no remote check. Delivery
works: 88 ms to the host's inbox, with a clear say-line note. A mouse user
sees a dead button with the title "Enter" and no reason, and gives up.
*Direction:* enable Send when the row is `dispatchable`, otherwise say why
(no hooks on the host, no credential yet).

### 3. `n` / alt+N goes by age, not by what a session waits for (Tessa)
Confirmed in code. `nextWaiting` sorts every session with `attention` by
`attention_since`, so a session blocked on a permission request (its work
stalled) ranks with sessions that merely finished a turn. With 16 sessions
it took **6 presses** of `n` to reach the blocked one (13 s estimated).
*Direction:* rank blocked (permission or question) before finished, or give
blocked ones their own key.

### 4. Worktree actions wait on git, even in a five-commit repository (Wren, Basil)
Observed. The same latencies hold for a release build, so this is git work,
not the debug build:

| Action | Debug | Release |
|---|---|---|
| Worktrees tab (`GET /api/worktrees`, 3 worktrees) | 2.4-3.4 s | 1.2-3.0 s |
| Project changes (`GET /api/project_changes`) | 1.4 s | 2.9 s |
| Merge / discard (`POST /api/worktree`) | 2.7-4.8 s | 2.3-3.4 s |
| Spawn plan before the worktree question (`POST /api/spawn`) | 0.2-2.5 s | 0.4-1.3 s |

Real repositories will be slower. *Direction:* count the git processes each
endpoint spawns (Windows process start is the likely cost), batch them, and
cache per HEAD/index mtime.

### 5. Discarding a worktree with unmerged commits asks twice (Wren)
Observed. The first prompt is "Remove this worktree and delete its branch?".
The dispatcher then refuses ("1 unmerged commit(s)") and a second confirm
asks again. That is two dialogs and two decisions for one intent, and 7-8 s
before the card went.
*Direction:* one dialog that already states the unmerged count.

### 6. A merge reports only in the say line, and the worktree stays (Wren, Basil)
Observed. "merge done: ..." appears beside the Send button, far from the
Merge button that was clicked. The card stays, now "0 ahead", so cleaning up
takes a separate Discard (finding 5). In Basil's run, Esc did not close
Project changes after the merge; its ✕ was needed (seen once; in Wren's run,
Esc closed it when no merge had happened).
*Direction:* show the result on the card, offer "merge and remove", and keep
Esc working after the action.

### 7. Background job from the New session dialog has no task field (Basil)
Observed (the dialog's hint says "the prompt box is its task"). Opening the
dialog first, which is the natural order, starts the job idle. It then needs
to be found and sent its task: 6 clicks and 4 keys, 16 s, the costliest
Basil step. ctrl+Enter from a session was 8 s.
*Direction:* a task box in the dialog, prefilled from the prompt box.

### 8. Closing a session: open it, ✕, confirm (Wren, Basil)
Observed. The ✕ shows only on the open tile, and a confirm follows: 4
interactions per close. (The 9.5 s close time is **sim**: the dispatcher
waits up to 8 s for `/exit`, and the simulated process does not read its
console. A real session exits sooner.)

### 9. Permission requests appear up to 3 s late (Tessa, Kai)
Confirmed in code. `drawPending` runs on every other 1.5 s tick (polling),
not from the stream. Measured: 2.4-3.6 s from park to the Allow button. This
is minor, but it is the one thing that blocks a session.

### 10. Permission rows have no keys (Kai)
Confirmed in code. Question cards have 1-9 and Enter; Allow / Deny / Console
rows have none. The keyboard persona had to reach for the mouse.

### 11. History: "Open" means resume, and the pop-up stays open (Sol)
Observed. The hit's buttons are Open / Fork / Copy cmd. Open resumed it, via
the worktree question because the folder was taken: 6.8 s to the tile. The
History pop-up was still open over the new session afterwards.

### 12. Smaller ones
- Every tile shows the prompt-cache countdown as a bare "-5" (minutes; the
  meaning is only in the hover title).
- Polling: one window makes 100-480 API calls a minute (`/api/conversation`
  and `/api/awaited` lead; `/api/usage` p95 550 ms). Unseen at this scale;
  worth watching with several windows or hosts.

## What is fast (no action needed)

ctrl+K to a session 157 ms. j/k 3-8 ms. Switching sessions 30-110 ms. A
400-turn conversation opens in 66 ms, and Earlier reaches its start in 4
clicks. Find with 100 matches: 286 ms. Send to delivered, about 1.5-2 s (the
mod's 2 s beat). The reply shows within ms of the turn's end. A queued
prompt runs 2.3 s after the turn ends. Stop reaches the session in 1.7 s.
/clear is followed in 2.4 s. A burst of three approvals takes 0.7 s. The
Chat Matrix loads in 170 ms. The dispatcher's working set stayed at 21-34 MB.

## Limits of this run

- One run per persona: the timings are indicative, not distributions.
- Claude Code is simulated: a launched session appears 2.5 s after launch,
  the mod beats every 2 s, and turns take seconds. Close time, Fleet Ask's
  answer, and the Settings host test's content (it tested a fake host) say
  nothing about the real thing.
- Harness defects found and fixed during the runs (not product findings): a
  `.qo` selector, waiting on a hidden element, beats only on a timer,
  malformed stop acks, `/clear` arriving as a command op, remote hooks not
  sent through the tunnel, permission requests parked on idle sessions.
